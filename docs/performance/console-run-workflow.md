# Canonical Switch Run: FTP + Sphaira Forwarder

**Owner-confirmed workflow (2026-11-02):** transfer the selected NRO and required files to the console over FTP; the owner creates/maintains a Sphaira HOME Menu forwarder with 4 CPU cores and 39-bit address space and launches the game through it. Retrieve logs through FTP after the run. The netloader/`nxlink` path in `tools/switch/nxtest.sh` is legacy and is not the acceptance path. Source for current tooling: `tools/switch/{ftp_logs.py,nxtest.sh}`; forwarder settings: `README_ru.md` §Forwarder.

1. **Before transfer:** assign Build ID, NRO SHA-256, shader-package/config hashes, Scenario ID and Run ID. Record the source and destination paths. The owner controls the console, FTP service, forwarder and saves. Do not replace a save or game asset. Confirm that the forwarder points to the NRO being tested; record the installed NRO hash if the FTP service can verify it, otherwise mark it unknown.
2. **Before launch:** record console model, firmware, handheld/docked, intended stock clocks, installed `naruto.toml`, core mask expected from the forwarder, background services and shader-cache class. A claimed four-core/39-bit run requires observed evidence in the profile/log where available, not just the forwarder's configuration.
3. **Launch:** the owner starts the forwarder manually and follows the frozen scenario. Write down start/end/checkpoint events and any deviation. Do not pretend `input_script` or PC replay was used when play was manual.
4. **Collect:** use `python3 tools/switch/ftp_run_summary.py RUN_ID` after a measured run. It reads the latest `naruto_NNN.log` and `logs/rex/rex_profile.log` over FTP into memory and retains only `docs/performance/runs/RUN_ID.md`. `tools/switch/ftp_logs.py` is now a compatibility entry point for the same compact collector; it no longer saves raw logs. If log rotation selected the wrong game log, pass `--game-log naruto_NNN.log`. Do not use `nxtest.sh` to collect a forwarder run.
5. **Summarize:** create one `console-log-summary-template.md` report per Run ID with source timestamps, observed clocks/core mask, resolution, segment metrics, errors, validity and missing fields. Keep only compact excerpts. Remove temporary full logs immediately. Keep per-frame numeric metrics outside Git if collected. Do not collect screenshots/video for routine performance runs; the existing owner capture already documents the hotspot location.

**Known endpoint:** `192.168.0.165:5000`, `/switch/naruto-nx` (read-only inspection, 2026-11-02); installed NRO/config/shader hashes are in `docs/project/console-install-snapshot.md`. The server's directory listings were empty while direct file operations worked; use known exact paths or diagnose listing separately. **Unknowns to verify:** FTP upload procedure, published release identity, whether the forwarder retains the intended 4-core/39-bit settings after an update, and whether every required metric survives file logging. Do not invent a deployment command or mark a run valid until these are recorded.

## Opt-in measured segment (new source; not yet console-validated)

For a **new measurement build**, set `naruto_measure_run_id = "RUN_ID"` in the installed `naruto.toml` and optionally `naruto_measure_duration_s = 30`. The ID must be unique for each execution and contain 1–64 ASCII letters, digits, hyphens or underscores. Record the updated TOML hash and a new config ID. The default empty Run ID leaves this telemetry off. Keep `switch_profile_report = true` and `log_to_file = true`; do not enable stack sampling for a headline run. The concrete diagnostic NRO and one-run TOML in `docs/project/measurement-build-2026-11-02.md` are now installed but have not been launched; see `docs/project/console-install-snapshot.md` §Diagnostic deployment.

Launch through the existing Sphaira forwarder, load the frozen save, position the camera and allow shader warm-up to finish. Then use the owner's FTP workflow to create `/switch/naruto-nx/logs/rex/measure_start_RUN_ID.flag` containing exactly `RUN_ID` and a newline. The game polls for that file once a second **before** the segment starts; it measures the configured duration once and writes one `[measure] START` and one `[measure] END` line. Use a fresh ID for every run so a stale flag cannot start a later run. The CPU profile and Renut report write the same Run ID, system-tick boundaries and tick frequency for each 10-second window. The collector includes only complete CPU/Renut windows inside the segment and requires matching tick frequency; a candidate report still needs manual save, route, build, mode, clock and checkpoint validation. No marker, an interrupted run or interval-buffer overflow leaves the report pending.

The END line contains bounded in-memory guest-Swap and host-present interval statistics: event/sample counts, FPS, p50/p95/p99/max ms and 1% low. Here 1% low means `1000 / mean(slowest ceil(1% of intervals) in ms)`. This callback is before proven panel scanout; do not label it a hardware display timestamp. Tick windows approximate the aggregation boundaries; counters and GPU results may be sampled shortly after the nominal end tick, so a fully contained 10-second window remains an aggregate, not a frame-exact critical-path trace. The measurement code does not yet expose an independent game-simulation clock, per-frame CPU/GPU critical path or automated route checkpoint. Compare its overhead against a Run ID-free **configuration of the same binary** at the same frozen scene before adopting the telemetry for acceptance.
