# Metric Catalog and Diagnostic Decisions

This catalog describes **what the v0.1.4 source can report**, not a validated baseline. A counter's existence does not prove it is present in a particular console log. Evidence: cited source paths and the compact `docs/archive/profile-2026-11-02.md` report. Read `measurement-protocol.md` before comparing runs. Targets and tolerances remain TBD until baseline and owner decision (`docs/project/quality-goals.md`).

## Measurement terms and limits

- **Guest Swap rate** counts game frames; **host present rate** counts completed host presentations. Keep both. Neither alone proves the screen displayed every frame or that the simulation ran at native speed. `app/src/renut_engine/perf/frame_stats.cpp` counts game frames at `OnGameFrame` and host presents at `OnRenderThreadFrame`; `sdk/src/ui/switch_perf.cpp` counter 0 uses host presents.
- **Frame interval** is elapsed time between consecutive events, not CPU or GPU execution time. Report which event was timed. Mean FPS is frames divided by elapsed seconds; compute 1% low only from individual frame intervals with a stated definition and sample count. Do not derive percentiles from 10-second averages.
- **Busy time** measures work on one stage; **wait time** reveals a dependency. CPU%, GPU ms, render busy ms and Swap-to-Swap ms may overlap. Do not add them or infer a bottleneck solely by comparing their means.
- A 10-second counter window is useful for triage; a module decision requires a frozen scene, observed clocks, shared start/end markers, repeated runs and a module-specific metric. A scene with pipeline creation or loading is a separate cold/load segment.

Availability for the **installed 0.1.4 binary**: **L** = logged with its current default settings, verify in the selected binary; **O** = existing optional diagnostic requiring a config change and overhead check; **M** = missing as a durable, scenario-aligned measurement. The source under development now has an opt-in segment summary; it is not evidence for the installed binary until built and run. The log's exact presence and completeness must be recorded per Run ID.

## Decision tree for a measured failure

1. **Validate first:** same save/route/camera, build/config, warm-up class, mode, resolution and observed clocks. Separate load/compile windows from steady gameplay. If any differ, classify the run before comparing FPS.
2. **Confirm user impact:** guest Swaps, host presents, frame-interval distribution and game-clock/checkpoint drift. If only 10-second means exist, report a preliminary symptom, not a quality pass/fail.
3. **Locate the limiting stage:** align main-thread busy/waits, render busy/waits, GPU time and present interval by frame or common marker. A near-full core suggests CPU work; high waits suggest a downstream dependency; high GPU work suggests GPU pressure. Verify with a controlled perturbation or stage profile before assigning ownership.
4. **Choose one module metric:** for CPU use named function/stack share or a measured wait; for render use busy time and draw-kind census; for GPU use work-by-kind time; for memory/load use bytes/latency/peak; for audio use misses or drift. State a falsifiable predicted direction and guardrails before any edit.
5. **Run A/B and regressions:** compare repeated valid runs at the same scene/config, including frame pacing, game speed, output correctness, memory and audio. A faster substage with unchanged or worse user-facing cadence is not a confirmed optimization.

**Current example, still preliminary:** `docs/archive/profile-2026-11-02.md` records 27–28 FPS windows, Main CPU at 92–94% of one core and a separate Renut log with mean GPU time around 23–25 ms/frame. This motivates a synchronized main-thread/wait test. The logs have no shared Run ID or proven scene identity, so the example does not rank a module for optimization.

## Telemetry work, in dependency order

1. Define one Run ID and shared start/end markers, system ticks and game-frame ordinals across the game and CPU logs; verify the scenario checkpoint separately. Source implementation exists, but a console run is still needed (`console-run-workflow.md`).
2. Collect guest-Swap and host-present intervals in a bounded in-memory segment and report count, p50/p95/p99/max and 1% low. Source implementation exists; validate its overhead and event semantics on console. Export a raw numeric stream outside Git only if a named failure requires frame-by-frame attribution.
3. Add or expose aligned CPU main/render busy and wait spans, GPU start/end or per-frame duration, and pipeline/load events only where the first measured failure needs them. Calibrate each diagnostic mode against the low-overhead run.
4. Add an independent game-clock/checkpoint marker for slow-motion and replay validity. Add file/load latency and video drift counters only for scenarios that exercise them.
