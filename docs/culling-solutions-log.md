# Журнал решений по оптимизации и куллингу: Naruto: Rise of a Ninja NX

В данном документе зафиксированы все исследованные подходы, гипотезы, успешные реализации и отклоненные решения в процессе оптимизации отрисовки открытого мира (деревня Коноха) для релиза **v0.1.4**.

---

## 1. Исходная проблема (v0.1.3 Baseline)

- **Количество Draw Calls**: >3400 вызовов на кадр в открытом мире Конохи.
- **Узкое место**: Ядро CPU 1 (основной поток PowerPC / генерация списков команд Direct3D).
- **Время рендер-потока на CPU**: **~34.8 мс/кадр** (приводило к просадкам ниже 20–25 FPS даже на разогнанном CPU и ~18–20 FPS на стоковых частотах).
- **Структура отрисовки по типам (`DispatchType`)**:
  - `DispatchType 5`: Модульная статическая геометрия мира (дома, крыши, заборы, мостовые) — **~2350 draws/кадр** (~70% всех вызовов!).
  - `DispatchType 14`: Динамические объекты, NPC, пропсы, интерактивные элементы — **~900–1000 draws/кадр**.
  - `DispatchType 13`: Shadow map pass и Z-depth проходы.

## 2. Что сработало (Успешные решения)

### 2.1. Dynamic Entity & Actor Culling (`sub_822A9A30`)
- **Суть**: Хук функции отсечения акторов перед добавлением в очередь рендера.
- **Реализация**:
  - Ограничение дистанции видимости второстепенных NPC и фоновых динамических объектов: `dist_sq > 60.0f * 60.0f` (60 метров для ambient crowd).
  - Сюжетные NPC, квестовые маркеры и интерактивные объекты не отсекаются.
- **Результат**: Снижение `DispatchType 14` на ~150–250 draws/кадр без визуальных артефактов в геймплее.

### 2.2. Per-Item Modular World Matrix Culling (`sub_820FD5F8`)
- **Суть**: Отсечение модульной статической геометрии на уровне элементов структуры `sub_820FD5F8`.
- **Реверс-инжиниринг структуры дескрипторов**:
  - `scene + 2824` хранит указатель на глобальную таблицу матриц трансформации 4x4 (float) текущей сцены.
  - `LoadU32(item_va + 32)` содержит индекс матрицы для конкретного меша/объекта.
  - Шаг матрицы в памяти: 64 байта (`index * 64`).
  - Мировые координаты объекта $(T_x, T_y, T_z)$ расположены со смещением `+48, +52, +56` от начала матрицы (`mptr + 48`).
  - Позиция камеры $(C_x, C_y, C_z)$ извлекается из инвертированной матрицы вида сцены по смещению `scene + 28`.
- **Логика отсечения**:
  - Вычисляется евклидово расстояние: $dx = T_x - C_x, \; dy = T_y - C_y, \; dz = T_z - C_z$.
  - Если $dx^2 + dy^2 + dz^2 > 160.0^2$ (дистанция свыше 160 метров), отрисовка объекта пропускается.
- **Результат**: Отрисовка `DispatchType 5` сократилась с 2350 до **690–1050 вызовов/кадр** (экономия свыше **1300–1400 draw calls на кадр**!).

### 2.3. Защита скайбокса (Skydome Protection)
- **Суть**: Предотвращение случайного отсечения геометрии неба.
- **Реализация**:
  - Скайбокс Конохи состоит из 5 концентрических полусфер с центром в `(-0.2, -6.8, -402.8)`.
  - Геометрия неба идентифицируется по:
    - Адресам вертексных буферов / геометрии: `geom_va == 0x42802bb0u` или `geom_va == 0x41608260u`.
    - Диапазонам материалов: `(mat_va & 0xFFFFF000u) == 0x40FBE000u` или `0x40D7D000u`.
    - Координате по оси Z: $T_z < -300.0f$.
  - Элементы неба безусловно пропускаются через фильтр куллинга.
- **Результат**: Небо стабильно синее, никаких мерцаний или черных провалов.

### 2.4. Геймплейный гейт (Gameplay Bounds Gate)
- **Суть**: Защита от куллинга во время экранов загрузки и смены локаций.
- **Реализация**:
  - При загрузке сейва камера игры временно перемещается за пределы игрового мира в точку `(-1020, -3970, -599)` (~4135 метров от центра деревни). Если куллинг активен в этот момент, вся геометрия мира отсекалась.
  - Добавлена проверка: куллинг активируется только тогда, когда камера находится в пределах активного мира:
    ```cpp
    bool in_gameplay = (std::abs(cam_x) < 400.0f && std::abs(cam_y) < 600.0f && std::abs(cam_z) < 100.0f);
    ```
- **Результат**: При загрузках и катсценах мир инициализируется корректно.

## 3. Что НЕ сработало (Ошибочные гипотезы и тупики)

### 3.1. Батчевый куллинг в `sub_820EDC80` (World Batch Iteration)
- **Гипотеза**: Отсекать целые группы/батчи геометрии разом на верхнем уровне цикла обхода.
- **Что проверялось**: Смещение `+0` и `+16` в массиве дескрипторов групп.
- **Почему не сработало**: По смещению `+0` располагались битовые флаги состояния (`0x15000`), а не координаты или радиусы видимости. В итоге куллинг либо не срабатывал вовсе, либо отсекал 100% сцены.

### 3.2. Куллинг по световому кэшу (`sub_820FFD30`)
- **Гипотеза**: Использовать координаты источников освещения/кэша объектов по смещению `cache_va + 52`.
- **Почему не сработало**: Функция `sub_820FFD30` оперирует глобальными параметрами освещения сцены (directional light, ambient), возвращая вектор `(1.0, 1.0, 1.0, 1.0)`, а не координаты конкретного меша.

### 3.3. Простое расстояние без исключения скайбокса
- **Гипотеза**: Единый радиус отсечения (160м) для всех элементов геометрии.
- **Почему не сработало**: Скайбокс физически привязан к точке с $Z = -402.8$. Как только игрок отходил более чем на 160 метров от центра деревни, небо попадало под радиус отсечения и исчезало, оставляя черный фон.

## 5. Смена узкого места (The New Bottleneck)

Благодаря снижению времени рендер-потока CPU до **19.68 мс** (что с запасом укладывается в бюджет 33.3 мс для 30 FPS):
- **CPU более не является главным ограничителем частоты кадров в Конохе.**
- **Новое узкое место**: **GPU (Tegra X1)**.
  - В открытых панорамных ракурсах деревни загрузка GPU достигает **99%**.
  - Время отрисовки GPU (**GPU frame time**) составляет **39.58 мс** (~25.3 FPS) на стоковой частоте 460.8 МГц при разрешении 720p.
  - Дальнейший фокус оптимизации для достижения железных 30/60 FPS на стоковых частотах должен быть направлен на **GPU fillrate, пиксельные шейдеры, Z-cull / Early-Z и динамическое разрешение**.
